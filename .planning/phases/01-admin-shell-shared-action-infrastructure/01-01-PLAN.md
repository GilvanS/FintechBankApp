<objective>
Build the shared confirmation + double-submit-protection infrastructure that every mutating admin action in Phases 2-6 will consume. This plan does not wire the hook into any live screen yet (Phase 1's admin panel shell has no real mutating actions — see 01-02) — it delivers a fully tested, standalone primitive per D-none (no CONTEXT.md exists for this phase; scope taken from ROADMAP.md Phase 1 goal and REQUIREMENTS.md SHELL-04/SHELL-05).

Deviation from milestone RESEARCH.md: RESEARCH.md's SUMMARY/ARCHITECTURE docs suggested a *new* native `<dialog>` (WEB) / `IonAlert` (MOBILE) component for confirmations. Direct codebase inspection this session found `WEB/contexts/GlobalDialogContext.tsx` — an existing, already-app-wide `useDialog()`/`showDialog()` confirm+info dialog, already imported and used in `Dashboard.tsx`, `HomeView.tsx`, and elsewhere, and its MOBILE mirror (`MOBILE/src/contexts/GlobalDialogContext.tsx`) is byte-identical (not Ionic-native — MOBILE does NOT use `IonAlert` for this). Building the shared admin hook on top of this existing, already-used-everywhere primitive is a smaller, more consistent change than introducing a second, competing confirmation UI — this is a planner discretion call (no locked CONTEXT.md decision to conflict with).

Purpose: Every later phase's mutating action (block user, force invoice cycle, purchase simulation, etc.) wraps its API call in this hook instead of hand-rolling its own confirm/disable-button/refetch logic — fixes PITFALLS.md Pitfall 1 (no idempotency/double-submit) and Pitfall 2 (missing confirmation) exactly once, for every subsequent phase.
Output: `WEB/hooks/useAdminAction.ts` (new), `WEB/contexts/GlobalDialogContext.tsx` (extended with a `danger` variant), both fully unit-tested.
</objective>
